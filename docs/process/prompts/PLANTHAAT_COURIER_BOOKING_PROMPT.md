## Product decisions (owner-approved, implement exactly)
1. **Each seller connects their own Steadfast merchant account** with their own API key and secret. The key is **optional**. An admin setting `courier.steadfast.required` (default **false**) can make it mandatory later: when true, a shop without an ACTIVE connection cannot publish products or receive new orders. Build the switch, leave it off.
2. A seller without an ACTIVE connection keeps the current manual flow unchanged (seller updates steps and delivered proof). Do not touch that flow in this prompt.
3. **Booking happens when the seller changes a shop order from CONFIRMED to PACKED**, and in the same action the rider pickup request is made automatically. There are **no** "call rider" or "retry pickup" buttons for sellers.
4. If booking fails, the order stays CONFIRMED and the seller sees a clear localized reason. The order is never PACKED without a successful booking for a connected seller.
5. Delivered, cancelled and similar outcomes come from the courier for connected, booked parcels. The seller's "mark delivered" action is hidden for those parcels (the courier is the source of truth). Manual sellers are unaffected.
6. SHIPPED is set automatically on the first **real** tracking update after booking (rules below). Implement and test this carefully.
7. COD dues, hiding products at the dues limit, advance payout totals: Prompt 3. The courier charge is borne by the seller; this prompt only records what the courier reports.
8. A seller changing a parcel's COD amount or address inside the Steadfast dashboard must flag the admin and appear on the order timeline. No automatic payout hold.
9. Customer-refused COD parcels: the seller bears delivery and return charges (Prompt 3), no platform fee on that order, and the customer's COD risk is marked (see mapping).

## Steadfast API facts to build against
Base URL `https://portal.packzy.com/api/v1` (env `STEADFAST_BASE_URL`, so tests can point at a fake). Headers `api-key` and `Secret-Key` on every call, `Content-Type: application/json`. Credentials are per seller connection, never global.
- `GET /get_balance` validates credentials and returns `current_balance` (delivered COD minus delivery charges minus 1% collection charge; **negative or low means the seller owes the courier**; Steadfast allows a due of up to ৳200 for prepaid parcels and then refuses bookings).
- `POST /create_order/bulk-order/extended` with a single entry in `data` is the booking call (human-readable errors; the response is HTTP 200 even for failure, so **read `data[0]`**: success has `status:"success"`, `consignment_id`, `tracking_code`, `tracking_link`; failure has `status:"error"` and an `error` array of sentences). Fields: `invoice` (letters, digits, `-`, `_` only; unique per Steadfast profile; ≤100), `recipient_name` (≤100), `recipient_phone` (11 digits starting 01), `recipient_address` (≤490), `cod_amount` (0 for prepaid; ≤1,000,000), `note` (≤480), `alternative_phone`, `item_description` (≤255), `total_lot`. Characters `{ } \ < > $` are replaced with spaces by Steadfast; sanitize ourselves first, and never compare the echoed address to what we sent.
- `POST /create_pickup_request` → 201. Fields: `address_id` (from the seller's Steadfast "Pickup Addresses" page, no API to create or list it), `police_station_id`, `address` (≤255), `contact_number` (11 digits starting 013–079), `note` (≤500), `estm_qty`. A second request for the same address while one is pending returns **409 `PICKUP_REQUEST_EXISTS` — treat as success**.
- `POST /create_return_request` → 201 with `consignment_id` or `invoice` and `reason` (≤500). **422** for already delivered, already returning, or duplicate open request.
- `GET /status_by_cid/{id}`, `/status_with_return_status_by_cid/{id}` (the only source that tells you a returned parcel is back), `/trackings_by_invoice/{invoice}` (every step: `tracking`: `[{consignment_id, tracking_type, text, created_at}]`, text is free-form English). **All status endpoints are cached 60 s by Steadfast; never poll one parcel faster than that.** `/parcel_states` and `/parcel_states/{state}` are live, paginated (`per_page` ≤100).
- Delivery statuses: `in_review` (every parcel starts here), `pending`, `hold`, `delivered_approval_pending`, `partial_delivered_approval_pending`, `cancelled_approval_pending`, `unknown_approval_pending`, `delivered`, `partial_delivered`, `cancelled`, `exceptional`, `unknown`. **Anything `*_approval_pending` is the rider's word, never settle or finalize on it.** Return statuses: `partial_delivered_return_processing|rider_assigned|received`, `cancelled_return_processing|rider_assigned|received`.
- Errors: 401 bad or revoked credentials (or parcel belongs to another profile), 403 inactive account or KYC to resubmit, 422/400 field errors, **429 after 10 failed auth attempts in 5 minutes locks the key for 60 minutes**, 500 server fault (retry with the same invoice is safe: duplicates are refused). Rate limits: 1,000 requests/min general, 6,000/min booking.
- **Never retry on 401.** Mark the connection `INVALID`, stop all calls for it, notify seller and admin. Hammering a bad key locks the account for an hour.

### Webhooks (from the Steadfast dashboard page)
Steadfast POSTs JSON to the callback URL and waits up to **5 seconds** for a 2xx. 5xx or unreachable → retries after 30 s and 2 min (3 attempts in total). A 4xx is **not** retried. Headers: `Content-Type: application/json`, `Authorization: Bearer <token>`, `X-Signature` = hex HMAC-SHA256 of the **raw request body** keyed with the token, `Idempotency-Key` (same value on retries), `User-Agent: Steadfast-Webhook/1.0`. The webhook belongs to the merchant's main account and its payload has **no seller identifier**, so the seller must be identified by a per-connection URL and token (below). Token characters allowed by Steadfast: letters, digits and `- _ . =` only. Events: `delivery_status`, `tracking_update`, `consignment_update`, `return_list_accepted`, `payment_request`, `cancel_request`, `return_request`, `pickup_request`, `user_update`.
`delivery_status` payload (the only documented one): `{"notification_type":"delivery_status","consignment_id":12345,"invoice":"INV-67890","cod_amount":1500.0,"status":"delivered","delivery_charge":100.0,"tracking_message":"…","updated_at":"2025-03-02 12:45:30"}` with `status` ∈ `pending | delivered | partial_delivered | cancelled | unknown`. The other event payloads are **not documented**: store every event raw, parse defensively (unknown fields ignored, missing fields tolerated), and never crash on a shape you have not seen. `updated_at` has no timezone: treat it as Asia/Dhaka, and log a warning when it is more than 15 minutes away from our receive time. Settlement-relevant: `delivery_charge` is the real courier charge and `cod_amount` is the amount; whether `cod_amount` means "collected" for `partial_delivered` is **unknown** (owner is asking Steadfast), so keep it as reported and flag partial deliveries for admin review.

## Data model (additive migrations only)
- `CourierConnection`: id, shopId (unique per provider), provider `STEADFAST`, ownerType `SELLER | PLATFORM` (only SELLER is used now), status `PENDING | ACTIVE | INVALID | DISABLED_BY_ADMIN`, `apiKeyEnc`, `secretKeyEnc`, `webhookPublicId` (unguessable random id used in the URL), `webhookTokenEnc` (generated by us, allowed charset only), `pickupAddressId` (Steadfast), `pickupContactNumber`, `pickupAddressText` (≤255), `defaultNote`, `lastVerifiedAt`, `lastBalance`, `lastBalanceAt`, `lastWebhookAt`, `lastErrorCode`, `createdAt/updatedAt`. Pickup thana reuses `Shop.pickupThanaId` and `Thana.steadfastPoliceStationId` from Prompt 1 (one source of truth).
- Encryption: AES-256-GCM, key from env `COURIER_SECRET_ENC_KEY` (base64, 32 bytes, validated at boot; store a key id on each row so the key can be rotated). Secrets are decrypted only inside the courier client for the duration of a call. **Never** returned to any client (masked display `••••1234` only), never logged, never in error reports, never in queue payloads. Deleting or disconnecting a connection wipes the ciphertext.
- On the shop order: `courierProvider`, `courierBookingStatus` (`NOT_BOOKED | BOOKING | BOOKED | FAILED`), `courierInvoice`, `courierConsignmentId`, `courierTrackingCode`, `courierTrackingLink`, `courierStatus` (raw latest), `courierStatusAt`, `courierBookedAt`, `courierBookedCodAmount`, `courierPickupStatus` (`NONE | REQUESTED | FAILED`), `courierReturnStatus` (raw), `courierReturnReceivedAt`, `courierDeliveryCharge` (from webhook), `courierReportedCodAmount`, `deliveredAtSource` (`COURIER | SELLER`).
- `CourierBookingAttempt` (shopOrderId, state, requestHash, outcome code, redacted response, startedAt, finishedAt): serializes booking per shop order (only one active attempt) and gives an audit trail.
- `CourierWebhookEvent` (connectionId, idempotencyKey unique per connection, notificationType, raw body, signatureValid, receivedAt, processedAt, processingError). Cap body at 64 KB.
- `CourierTrackingEvent` (shopOrderId, text, courierCreatedAt, source `WEBHOOK | POLL | BOOKING`, dedupe hash unique per shop order). Stored for Prompt 4's customer timeline.
- `CourierIssue` (shopOrderId nullable, connectionId, type, status `OPEN | RESOLVED | DISMISSED`, details json, createdAt, resolvedBy): types `HOLD`, `EXCEPTIONAL`, `UNKNOWN_STATUS`, `PARTIAL_DELIVERY`, `CONSIGNMENT_CHANGED`, `RETURN_REQUESTED_BY_HUB`, `PICKUP_FAILED`, `BOOKING_REPEATEDLY_FAILED`, `CONNECTION_INVALID`, `WEBHOOK_SIGNATURE_FAILURES`.
- `CourierJob` (type, payload ref ids only, runAt, attempts, lockedAt, lastError): a small database-backed job table processed by the existing scheduler with `FOR UPDATE SKIP LOCKED`, used for pickup retries, polling, webhook processing and return follow-up. No new infrastructure.

## Booking and pickup flow (the PACKED action)
Existing endpoint for status change stays; extend it for connected shops. Sequence for CONFIRMED → PACKED when the shop has an ACTIVE connection:
1. Preconditions with distinct error codes: connection ACTIVE; pickup details complete; the shop order is not already BOOKED; for advance payments the order's payment is PAID (the existing shipping gate stays); the delivery address has a valid 11-digit phone (normalize `+88`/`88` prefixes). Fail early with the code if not.
2. Create a `CourierBookingAttempt` in state BOOKING (unique active attempt per shop order; a second click while one is running returns "booking in progress" instead of booking again). **Do not hold a database transaction open during the HTTP call.**
3. Build the payload. `invoice` = `PH-<shopOrderNumber>` sanitized to the allowed charset and ≤100, deterministic so retries hit the same invoice. `recipient_name`, `recipient_phone`, `recipient_address` from the order's address snapshot (district, thana, area, details), sanitized and truncated. `cod_amount` = the **shop-order payable on delivery** for COD (products plus the delivery charge the customer was shown; the exact stored figure) and **0 for advance**; never recompute prices client-side, take the stored snapshot. `note` = customer delivery note if any plus the seller's default rider note, ≤480. `item_description` = `Plants (<n> items)` plus a short product list if it fits ≤255. `total_lot` = total quantity. `exchange` omitted, `delivery_type` omitted (home delivery).
4. Call the booking endpoint (timeout 10 s). Interpret `data[0]`. On success, in one short transaction: store the courier fields, set BOOKED, set the shop order to PACKED with a history entry (`source COURIER_BOOKING`), write the first tracking event, and enqueue the pickup job. On a handled failure map to reasons: `COURIER_AUTH_FAILED` (401 → connection INVALID), `COURIER_ACCOUNT_RESTRICTED` (403), `COURIER_VALIDATION` (field sentences shown, e.g. bad phone), `COURIER_RATE_LIMITED` (429), `COURIER_UNAVAILABLE` (network, timeout, 5xx), `COURIER_BOOKING_REFUSED` (anything else, including a likely low-balance refusal). **Steadfast's wording for a balance refusal is unknown**: log the raw sentence in the attempt record and show the seller a safe message plus the courier's own sentence in a collapsible "Details", and suggest checking the Steadfast balance. Order stays CONFIRMED.
5. **Unknown outcome** (timeout or 5xx): do not guess. Mark the attempt UNKNOWN and reconcile before allowing another booking: `GET /status_by_invoice/{invoice}`; if the parcel exists, adopt it (fetch `/trackings_by_invoice/{invoice}` to read `consignment_id`; the tracking code and link may be unavailable in this case, store null and continue). If it does not exist, treat as failed and allow retry. A `THIS_INVOICE_ALREADY_EXISTS` style error must lead to the same adoption path, not an error to the seller.
6. **Pickup** (after the PACKED commit, never inside it): job `PICKUP_REQUEST` → `POST /create_pickup_request` with the shop's address id, thana, address text, contact number, note, `estm_qty` = number of PACKED shop orders of that shop not yet picked up (at least 1). 201 or 409 = success (`REQUESTED`). Network or 5xx: retry with backoff (30 s, 2 min, 10 min, 1 h, 6 h). 401/403/422 or exhausted retries: `courierPickupStatus=FAILED`, open a `PICKUP_FAILED` issue, notify the seller (with the reason: usually a wrong address id) and the admin. A pickup failure never rolls back the booking or the PACKED state. Admin (only) may retry pickup from the admin order view.
7. Notifications through the existing notification system (realtime and bell): seller on booking failure, connection invalid, pickup failed, low balance; admin on issues. Customer order status notifications continue to fire from the normal state changes.

## Cancellation after booking (returns)
Reuse the existing cancellation flows (customer request for CONFIRMED/PACKED, seller or admin cancel). Rules: if the shop order has **no** booked parcel, nothing courier-related happens. If it **has** a BOOKED parcel and is not delivered, an approved cancellation calls `POST /create_return_request` (`invoice`, `reason`). 201, or a 422 for duplicate or already returning, counts as "return requested". A 422 for **already delivered** blocks the cancellation with a clear message (the customer must use the normal return and complaint route). Network failure: retry job; the cancellation shows "return pending". **Do not restock at cancel time for booked parcels**: stock stays reserved until the courier reports `cancelled_return_received` (poll `/status_with_return_status_by_cid`) or an admin confirms manually; then follow the existing restock-choice logic (setting `courier.autoRestockOnReturnReceived`, default false: when false, notify seller and let them confirm the restock). Money refunds for advance payments keep following the existing cancellation and refund rules; this task does not change them.

## Webhook receiver
`POST /api/v1/webhooks/steadfast/:publicId`, public (no cookie auth, no OriginGuard, excluded from CSRF), strict body-size limit (64 KB), throttled per publicId and per IP. Capture the **raw body** (do not verify against re-serialized JSON). Steps: look up the connection by `publicId` (unknown → 404); require `Authorization: Bearer <token>` and `X-Signature`; compute HMAC-SHA256 of the raw body with the connection's token; compare with `crypto.timingSafeEqual` after a length check; any mismatch → 401 and count it (many failures open a `WEBHOOK_SIGNATURE_FAILURES` issue). Valid: insert `CourierWebhookEvent` (idempotency key unique per connection; a duplicate returns 200 immediately) and **return 200 within a second**, then process from the job table. If the insert fails return 500 so Steadfast retries. Never process inline. Update `lastWebhookAt`. Provide `scripts/steadfast-webhook-simulate.ts` that sends correctly signed sample events to a local server for development.
Event handling (always scoped to the connection's own shop; an invoice that does not belong to this shop is ignored and logged, never applied):
- `delivery_status`: apply the status mapping below; store `delivery_charge` and `cod_amount`.
- `tracking_update`: store a tracking event (dedupe by text and time), run the SHIPPED rule.
- `consignment_update`: compare the reported COD amount and address (when present in the payload) to our booked snapshot; any difference opens `CONSIGNMENT_CHANGED` for admin, adds a timeline entry for the seller and admin, and changes nothing else. If the payload has no usable fields, store it and fetch the parcel's current data only if an endpoint exists; otherwise flag as "changed, details unknown".
- `return_request` (the hub asks the seller to agree to cancel): `RETURN_REQUESTED_BY_HUB` issue and a seller notification (the seller must respond in the Steadfast dashboard).
- `return_list_accepted`: store; then immediately poll the affected parcel's return status.
- `payment_request`, `cancel_request`, `pickup_request`, `user_update`: store raw and show in the admin event viewer; `payment_request` also sets a flag the settlement prompt will use. No other effect.

## Polling (the safety net, because webhooks can be lost and are not configured for every seller)
A scheduled job (existing scheduler, every 2 minutes) selects shop orders that are BOOKED and not terminal, with `courierStatusAt` older than their interval, and checks them with `GET /status_with_return_status_by_cid/{id}`. Interval by age since booking: every 5 minutes for 6 hours, every 15 minutes up to 48 hours, then hourly up to 14 days, then stop and open an issue if still non-terminal. Add jitter, spread across connections, cap concurrent requests per connection (for example 3) and requests per connection per minute (for example 60), skip connections that are not ACTIVE, and **never poll a parcel more than once per 60 seconds**. For the customer or seller opening an order, an on-demand refresh is allowed at most once per 60 seconds per parcel. Poll results go through the **same mapping function** as webhooks, so both sources always agree.
`trackings_by_invoice` is fetched on demand and by the poller for in-flight parcels at most every 5 minutes, storing new entries as `CourierTrackingEvent`.

## Status mapping (one pure, well-tested function)
Inputs: current shop order status, raw courier status, optional return status, event time, source. Output: transitions plus issues. Rules:
- Raw `in_review` and `pending`: no transition (PACKED stays PACKED). `hold`, `exceptional`, `unknown`, `unknown_approval_pending`: no transition, open the matching issue, notify seller and admin.
- `delivered_approval_pending`, `partial_delivered_approval_pending`, `cancelled_approval_pending`: no transition, record on the timeline only. **Never** start the return window, settle or release money on these.
- **SHIPPED rule:** while the shop order is PACKED and booked, move to SHIPPED when a **real** tracking entry exists after booking: an entry whose creation time is later than the booking time and whose text does not match the booking-creation text (case-insensitive match of "consignment created"). A raw status of `pending` alone is not enough. If `delivered`, `partial_delivered` or `cancelled` arrives while still PACKED (SHIPPED was missed), pass through SHIPPED first so the history is complete. Keep the matcher in one place, with the creation-text patterns configurable in a constant and covered by tests using the real examples ("Consignment created by Sender(API).", "Parcel received at Dhanmondi hub.").
- `delivered` (confirmed): SHIPPED → DELIVERED. `deliveredAt` = the event's `updated_at` interpreted as Asia/Dhaka, **clamped** to not be in the future and not before the booking time; log the skew when it differs from receive time by more than 15 minutes. This starts the existing return window logic exactly as a seller-marked delivery does today, with `deliveredAtSource=COURIER`. No seller proof photo is required for courier-confirmed delivery.
- `partial_delivered` (confirmed): no automatic transition; open `PARTIAL_DELIVERY` for admin review (amount and parcel details attached) and keep the order out of any automatic release.
- `cancelled` (confirmed): SHIPPED/PACKED → FAILED_DELIVERY, record the reason text, and start return tracking. If the payment method was COD, add a COD risk event for the customer through the existing COD risk module as a soft signal with type `COURIER_CANCELLED` (admin can dismiss it); do not auto-ban. The seller bears the courier charges (Prompt 3).
- Return status `cancelled_return_received` (and `partial_delivered_return_received`): set `courierReturnReceivedAt`, notify the seller, then follow the restock rule above.
- Terminal states are sticky: `delivered`, `partial_delivered`, `cancelled` are never overwritten by an older or lower-ranked signal (compare event time and status rank; a late `pending` webhook must not move a delivered order back). Only an admin override changes them.
- Idempotent: processing the same event twice, or a webhook and a poll carrying the same status, must produce exactly one history entry and one notification.
